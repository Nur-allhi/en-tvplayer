> **Status:** Approved · **Date:** 2026-11-15 · **Owner:** repo maintainer

## 0. Executive summary

EN IPTV Player v4 turns the current working app into a **platform**:

| Today (v3.2.0) | v4.0.0 |
|-----------------|---------|
| 4 monolithic files (`main.js` 1587, `player.js` 1669, `ui.js` 1463, `settings.js` 1066 LOC) | Every module ≤ 300 LOC |
| 74 exports crammed into `ui.js` | One owner per module, re-export hubs |
| Live IPTV only | Live IPTV **+** Movies **+** TV Series |
| Feature removal = surgery | Feature removal = one registry line |
| No CI | CI gates every merge |
| Implicit knowledge | Tickets, changelog, session log, compat matrix |

**Non-negotiable constraint:** v3.2.0 keeps working. Every v4 change ships
behind a version guard; the v3.2.0 WGT stays installable and updatable.

## 1. Goals and success criteria

### 1.1 Goals

| # | Goal | Measurable criterion |
|---|------|---------------------|
| G1 | **Modular** | Every source file ≤ 300 LOC; no file exports > 15 symbols; zero circular imports |
| G2 | **Modern** | Design tokens in CSS vars; ≥ 4.5:1 text contrast; keyboard+remote parity on every screen |
| G3 | **Optimized** | Bundle ≤ 1.1 MB raw; cold boot → first frame ≤ 3 s (cached); channel switch ≤ 1.5 s; zero unbounded loops |
| G4 | **Extensible** | New feature = ≤ 30 LOC of wiring; feature removal = 1 config line, no code edits |
| G5 | **Safe** | 100% of pure logic unit-tested; CI gates every merge to `dev`; v3.2.0 remains installable |
| G6 | **Multi-modal** | Live TV, Movies, and Series share one playback engine and one library UX |

### 1.2 Explicit non-goals for v4.0.0

- ❌ No cloud service, accounts, or sync (stays serverless, per README)
- ❌ No VOD transcoding, hosting, or DRM for movies (streams only)
- ❌ No scraping of copyrighted catalogs (public-domain sources only)
- ❌ No Tizen 4.0 support — **ruled out by measurement**, see `docs/TIZEN_COMPAT.md` §3.1
- ❌ No framework migration (React/Vue) — a 950 KB bundle has no room for a runtime

### 3.2 Module rules (enforced by CI)

1. **≤ 300 LOC** per file. CI fails the build otherwise.
2. **≤ 15 exports** per file. Split rather than grow a hub.
3. **No circular imports.** `scripts/validate-modularity.mjs` walks the graph.
4. **`lib/` and `logic.js` are DOM-free** — required for Vitest (node env).
5. **Imports flow downward only:**
   `main.js → app/ → player|ui|settings|features → lib|state`
   Never upward. `app/` never imports `ui/` internals directly — it goes
   through the `ui/index.js` hub.
6. **Every public function has a test** in a colocated `*.test.js`.
7. **Re-export hubs preserve the old API.** After splitting, `ui.js` exports
   exactly the same 74 names as before, so `main.js` imports never change.
   This is the key trick that makes the split behaviour-preserving.

### 3.3 Plugin registry — the "remove a feature" mechanism

```js
// app/plugins.js
export const FEATURES = {
  search: { load: () => import('../features/search.js'), enabled: true },
  favorites: { load: () => import('../features/favorites.js'), enabled: true },
  infoBar: { load: () => import('../features/info-bar.js'), enabled: true },
  vod: { load: () => import('../features/vod.js'), enabled: true },
};

export function isEnabled(name) {
  return FEATURES[name]?.enabled === true;
}
```

> ⚠️ **Build constraint (verified):** the app builds with
> `output.format: 'iife'`. Rollup **rejects** dynamic `import()` under IIFE
> ("UMD and IIFE output formats are not supported for code-splitting builds").
> The v4 config therefore sets `inlineDynamicImports: true`, which keeps a
> single IIFE file while preserving the `import()` call sites. If a future
> build switches to `es` format, the registry switches to real lazy chunks
> for free.
>
> Verified locally: `rollup({format:'iife'})` → build failure;
> `format:'iife', inlineDynamicImports:true` → build OK, 0 `import()` left in
> the output.

**Adding a feature:** create `features/x.js`, add one line to `FEATURES`.
**Removing a feature:** set `enabled: false`, or delete the file and the line.
**Nothing else in the app changes.** The registry is the only coupling point.

Feature contract:

```js
export default {
  id: 'favorites',
  init(ctx) {},          // called once at boot
  destroy() {},          // called on teardown
  routes: {},            // optional remote-action handlers
  menuEntries: [],       // optional right-sidebar rows
};
```

### 3.4 State container

```js
// state/index.js
export function createStore(initial) {
  let state = { ...initial };
  const listeners = new Set();
  return {
    get: () => state,
    set(patch) { state = { ...state, ...patch }; listeners.forEach((fn) => fn(state)); },
    subscribe(fn) { listeners.add(fn); return () => listeners.delete(fn); },
  };
}
```

Stores: `appState` (channels, current channel, groups), `uiState` (sidebar,
focus), `vodState` (library, search). Pure, testable, no DOM.

**Goal:** visual refresh without touching playback.

### Phase 8 — VOD: movies + series (M8)

**Goal:** live TV and VOD in one app, one engine.

**8.1 Data model** (`lib/media-id.js`, `state/vod.js`)

```js
/**
 * @typedef {Object} MediaEntry
 * @property {string} id        stable slug (hash of normalised URL)
 * @property {string} title
 * @property {string} url       direct stream URL
 * @property {'movie'|'series'} type
 * @property {number} [year]
 * @property {string[]} [genres]
 * @property {number} [duration] seconds
 * @property {Episode[]} [episodes]  series only
 * @property {number} [resumeAt]     seconds
 */

/**
 * @typedef {Object} Episode
 * @property {string} id
 * @property {string} title
 * @property {string} url
 * @property {number} season
 * @property {number} number
 */
```

**8.2 Sources — no scraping of arbitrary sites**

CORS is the hard constraint: the TV fetches the stream directly, so any
source that does not send `Access-Control-Allow-Origin` is unusable. The v4
plan supports **three source kinds**, all user-supplied:

| Kind | Example | How it works |
|------|---------|--------------|
| Direct stream URL | `https://host/movie.mp4` | Played as-is by Shaka |
| M3U-style playlist | `https://host/vod.m3u` | Reuses the existing M3U parser |
| JSON manifest | `https://host/library.json` | Fetched, parsed as `MediaEntry[]` |

A user-supplied **direct URL** or **JSON manifest** is the supported path. We
do **not** ship an archive.org/IMDb scraper: those pages are not CORS-readable
from the TV, and page-scraping breaks whenever the site changes. If a user
has a JSON manifest they control, it works; if they only have a web page, we
tell them plainly what is needed.

> Note: the Tizen native AVPlay pipeline ignores CORS, so direct URLs that the
> browser stack refuses can still play through `player/avplay.js`. That is a
> real fallback, not a workaround.

**8.3 UI**

`ui/library.js` renders a Movies / Series browser inside the existing left
sidebar (reusing the group-list pattern). Remote flow:

- Left sidebar → first row **"Movies"** / **"Series"** (alongside groups)
- OK on a movie → detail card → OK plays
- OK on a series → season/episode list → OK plays
- Right menu gains **Audio**, **Subtitles**, **Quality** pickers
- Back always returns one level; never strands

**8.4 Playback**

Reuses the existing engine: `player.load.js` → Shaka (with ClearKey when the
manifest declares it) → native AVPlay fallback. New work is limited to:
subtitle track selection (Shaka exposes text tracks), audio track selection
(already exists in `player/stream.js`), and resume position persistence.

**Exit criteria:** a movie plays end-to-end from a direct URL; a series
browses to an episode and plays; resume position restored; audio/subtitle
pickers work; all remote-only.

### Phase 9 — Tizen 5.0 compatibility (M9)

**Goal:** raise the floor from Tizen 5.0 to Tizen 5.0 *reliably*, and
gracefully degrade on anything older.

1. `lib/capabilities.js` (Phase 1) as the single probe.
2. `features/tizen-compat.js` — shims for `AbortController` (only if missing),
   `trimStart`, `ResizeObserver`; all **guarded** and **small**.
3. Engine selection: if Shaka is unusable but AVPlay exists → native-only
   mode (no DRM — say so in the UI).
4. `app/about.js` shows "Engine: Shaka / Native / Browser" + TV API version +
   a "Copy diagnostics" button (Phase 10).

**Exit criteria:** app boots and plays on a Tizen 5.0 TV; on an unsupported
engine the user gets a plain-language message, not a blank screen.

### Phase 10 — Diagnostics & polish (M10, → v4.1)

- In-memory log ring buffer (200 entries) + "Copy diagnostics" in Settings → About

- Favorites (feature plugin)

## 8. Signing key — release blocker (read before any release)

`scripts/release.mjs` refuses to run without `tizen/author-key.pem`, and it is
correct to refuse: **a different key makes the TV treat the update as a new
app and wipes every user's settings, playlists and favourites.**

| Key that signed every released WGT (v3.0.2 → v3.2.0) | created **2026-08-28** |
| SHA-1 fingerprint | `8F:73:83:29:93:CC:1E:13:16:AE:89:00:E0:AA:BD:5B:50:80:90:23` |
| SHA-256 fingerprint | `40:71:40:30:04:D9:49:25:55:68:FF:44:B8:36:47:35:22:52:89:61:E6:0F:BE:57:3A:9B:28:5B:7D:B7:51:43` |

**Verification performed:**

- The certificate matches all six released WGTs byte for byte.
- `openssl rsa -check` → `RSA key ok` (the key is mathematically valid).
- The private key's modulus matches the certificate's (it is its pair).
- A WGT built with it carries a **byte-identical signer certificate** to the
  released v3.2.0 (853 bytes, identical).

### 8.2 The guard that now prevents a repeat

The mistake happened because the packager **silently minted a new key** when
it found none, and nobody noticed until a release was nearly cut. That is now
impossible:

- `tizen/author-cert.sha256` — the expected certificate fingerprint,
  **committed to the repo**. The key stays gitignored; its fingerprint is
  public and is what proves a build carries the same app identity as every
  previous release.
- `tizen/package.mjs` compares the installed certificate against that file
  and **aborts the build** on mismatch, printing both fingerprints.
- Key generation now prints a loud warning instead of doing it silently.

Verified by test: with a freshly generated (wrong) certificate installed,
`npm run tizen` exits non-zero and refuses to build.

### 8.3 Procedure before any v4 release

1. Confirm the key is present: `ls -l tizen/author-key.pem`.
2. Confirm it is the right one:
   ```bash
   openssl x509 -in tizen/author-cert.pem -noout -fingerprint -sha256 -dates
   # must print 40:71:40:30:04:D9:49:25:55:68:FF:44:B8:36:47:35:22:52:89:61:E6:0F:BE:57:3A:9B:28:5B:7D:B7:51:43
   # and notBefore Aug 28 06:55:23 2026 GMT
   ```
3. `npm run tizen` — the packager enforces step 2 itself and refuses to
   build on a mismatch. A build that succeeds is a build with the right key.
4. Keep the off-machine encrypted backup. A second copy in a password
   manager is cheap insurance.

## 11. Definition of done (per ticket)

A ticket is done when **all** of these hold:

1. Code ≤ 300 LOC per file, ≤ 15 exports per file.
2. New pure logic has unit tests; a bug fix has a regression test written
   **first** (reproduce → fix → green).
3. `npm test`, `npm run lint`, `npm run build`, `npm run validate` all pass.
4. The self-review checklist (`docs/BRANCHING.md` §6) is satisfied.
5. `CHANGELOG.md` `[Unreleased]` updated if user-visible.
6. A `docs/SESSION_LOG.md` entry written.
7. Ticket moved to *Done* with the merge SHA.
8. TV-verified when it touches playback, remote input, or DRM (desktop
   verification is a smoke test, not a substitute).

**Merge rule:** the branch merges into `dev` only after items 1–4 are green.
Items 5–8 can follow in the same session or the next one — but the session
log entry (6) is what makes the rest recoverable.
